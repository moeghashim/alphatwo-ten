The review, reconciled

The tool-execution & state architecture went out for adversarial review to Codex and AMP, independently. Both came back sound-with-changes. They reached the same conclusion from two different directions — and this page is the reconciliation: the verdict, every change decided, the one conflict resolved, the one decision still open, and the order we make the edits in.

Companions: the design (source of truth) · the tool contract · the build plan · the stack.

1 · The verdict

sound-with-changes  ×2. Keep the shape — ephemeral Node-only µVM tools, the brain / Postgres / R2 storage split, plan/apply with a policy gate, and the CLI contract. Don't rip anything out. There is one structural gap, and both reviewers landed on it.

2 · Two reviews, one gap

Codex and AMP described the same missing piece in different vocabulary:

ReviewerHow they framed the gap
Codex — authority Execution authority belongs to the platform, not the disposable µVM. Tools propose; the platform disposes. A validated envelope after execution isn't control — if untrusted tool code holds a write credential before the gate, the gate is advisory.
AMP — durability The durable orchestration semantics your three hardest guarantees depend on were never written down. They're asserted in prose, not pinned in a contract — so they'll produce your first real incident.

Authority and durability are the same boundary seen from two sides. The three guarantees that quietly rest on it:

1. Any job can crash or be re-run at any point with zero data loss and no double-effect.

2. No tool moves money or mutates a live system outside an approved policy.

3. Results are comparable across the whole fleet, so the system can self-improve from real outcomes.

3 · Not a different shape — a missing layer

Neither reviewer wants a redesign. The fix is to add one layer to the architecture we have: a durable orchestration boundary, with the µVM modelled as an external async activity — never a durable worker.

Keep — unchanged

The shape is right

  • CLI contract (CONTRACT.md)
  • Ephemeral Node-only µVM tools
  • Brain / Postgres / R2 split
  • plan / apply + policy gate
Add — the missing spec

Durable orchestration

  • Job state machine: queued → dispatched → running → awaiting_approval → applying → {succeeded · partial · failed · timed_out}
  • Per-apply-item idempotency ledger
  • Outbox / inbox dedupe — unique(job_id, event, external_id)
  • Leases + per-agent no-overlap locks
  • Approval as a durable wait (hours/days)
  • Reconciliation: effect-happened-but-webhook-lost

backend  For the MVP this is a Postgres-backed state machine + transactional outbox/inbox — no new vendor. A durable engine (Inngest / Restate) is a later swap behind the same interface. Note the trap both reviews flag: an engine gives you timers, retries, and waits — it does not give exactly-once external effects, trustworthy audit, or spend caps. Those come from idempotency keys, credential scoping, and platform-side ledgers regardless of engine. Don't let "we added Inngest" create false confidence.

Assembled, the whole system looks like this — the new layer in clay, everything else already in place. Maestro stops firing µVMs directly; every job now routes through the control plane, which dispatches propose-only µVMs, finalizes all durable writes, and brokers any money-moving call.

5 · The conflict, resolved — platform-finalized audit

The docs contradicted themselves: design §8 said the µVM commits the brain and writes Postgres inside the run; CONTRACT §11 and the build MVP said only the platform writes after validation. So the audit record design §8 sells as "cryptographically auditable" was authored by the least-trusted component.

Before (conflicted)After (platform-finalized)
µVM writes Postgres + commits the brain in-run. The HMAC proves "a µVM with our token wrote this text" — not "a validated action occurred." µVM returns envelope + artifacts + proposed brain diffs. The platform validates, dedupes the webhook, verifies the plan checksum, writes action_log, renders the canonical history.html/timeline.html from a trusted template over validated data, and commits with the scoped token.

Tools still author report content and propose updates — only authority over the canonical record moves. The brain stays customer-owned and exportable, so design §8's portability claims survive. We keep the platform a generic finalizer, not a domain author, so the "near-free new tool" goal survives too. Bonus: the µVM no longer needs a GitHub write token at all — the credential surface shrinks. design.html stays source of truth; CONTRACT.md reconciles downstream.

6 · The one open decision

The only thing the two reviews don't settle between them: who holds the external write credential during apply?

OptionWhat it means
Codex — broker (stronger)The µVM never holds the credential for a gated action. A platform broker holds it and executes only the approved plan. The gate is strictly authoritative.
AMP — scoped cred (lighter)The apply-µVM may hold a tightly-scoped write credential; safety comes from idempotency keys + the action-items ledger + gate recomputation + reconciliation.

Recommendation — decide per provider, by one rule: can the write credential be scoped tightly enough, and the provider enforce a hard cap, that a misbehaving µVM holding it cannot exceed the already-approved blast radius?

Yes (token scoped to specific campaigns + provider-side hard spend cap) → AMP's lighter model is enough.   No (broad account token) → Codex's broker is required.

Default to the broker; allow scoped-cred only where scoping + caps are verified. Either way, changes 1, 2, 6, 7 are required regardless. Not due until the first money-moving tool — the MVP has no external writes — so it doesn't block starting.
